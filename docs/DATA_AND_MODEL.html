Epic Game Pass When? / Data and model reference

Arrival Model Handbook

How this system predicts when a game will show up free on Xbox Game Pass, PS Plus Extra, the Epic Games Store, or Humble Choice — what data feeds it, what it actually learns, how good it really is, and where it is still wrong.

Written 23 Aug 2026 Model v5 quantile bundle Plan v1.8, Phase 5 Branch phase-5-model

The question the system answers

Scope

A user types a game name and picks a service. The system answers when will this be free there — as a month, with a range around it.

That makes this a time-to-event problem, not a classification one. The quantity being predicted is the number of days between a game's release and the day it lands on the service. Framing matters more than it looks: because the thing being predicted is a duration measured forward from the past, any validation that shuffles rows at random lets the model see the future. That mistake was in this codebase for most of its life, and correcting it changed the reported error by roughly a factor of two.

Four services, four separate models. Nothing is shared between platforms except the code — each has its own dataset, its own target distribution, and its own trained bundle.

The four datasets

Every platform's history is maintained by hand somewhere on the public internet, and each one arrives in a different shape. This is the least glamorous and most fragile part of the system.

Canonical schema

Whatever the source looks like, ingest flattens it to eight columns. Every downstream stage reads only these.

game_name title as scraped; the join key everywhere release_date MM/DD/YYYY, often blank until RAWG fills it Added to Service MM/DD/YYYY, the event date, and the target's endpoint Removed from Service MM/DD/YYYY or blank; carried, not modelled metacritic_score numeric, sparse publisher RAWG-filled; comma-separated, first value wins developer RAWG-filled; carried, not modelled System platform string from the source

Spreadsheet exports are position-dependent

Ingest reads the two community spreadsheets by hardcoded column index, not by header name. If a maintainer inserts a column, ingest silently reads the wrong field and writes plausible-looking wrong data with no error. Verify the header row against the expected index map before trusting any refresh.

Also: exporting those sheets as CSV yields the displayed value (Jan 2026), while xlsx yields the underlying cell (2026-01-01). Same sheet, different precision. Formats are not interchangeable.

How data moves

Five stages

The pipeline is an importable Python package; run.ipynb at the repo root is a thin orchestrator that calls each stage in order. No stage reaches past its neighbours.

data/raw/ ingest data/processed/ enrich data/canonical/ scrape dumps ----------> *_Processed.csv ----------> Epic/Xbox/PS/HB.csv | train | v apps/backend/ deploy models/ model_<key>.pkl serving copy <---------- bundles + canonical CSVs
  • ingest parses each raw dump into the eight-column schema. Pure parsing, no network.
  • enrich fills publisher, developer, release_date and metacritic_score from the RAWG API, then merges into canonical. It builds its lookup cache from the existing canonical files first, so only genuinely new titles cost an API call.
  • train reads canonical and writes one bundle per platform.
  • backtest scores the model against naive baselines and acts as the quality gate.
  • deploy copies canonical CSVs and bundles into apps/backend/, which is the Docker build context.

data/processed/ is gitignored and fully regenerable. Canonical CSVs and current bundles are tracked, because they are what the backend serves.

The target

What the model is fitted on

The label is days_to_service, the gap between release and arrival:

days_to_service = (Added to Service) - (release_date) in days rows are dropped unless: days_to_service is not null days_to_service >= 1 day-one arrivals and bad dates are excluded primary_publisher not in ("Unknown", "") primary_publisher = publisher.split(",")[0].strip()

Models are fitted on log(days) and exponentiated back at prediction time. That choice matters when reading errors: the model is being optimised for proportional accuracy, so being six months off on a three-year wait counts as a smaller mistake than being six months off on a two-month wait. Any error analysis should be done in log space and only then reported in days.

Because of the >= 1 filter and the publisher requirement, the trainable set is smaller than the row counts above. After the August 2026 refresh: 2,141 usable rows for Xbox, 2,279 for PS Plus, 1,083 for Humble and 578 for Epic. Median wait varies enormously by service — 530 days on Humble against 1,392 on PS Plus — which is why the four models share no parameters.

Of those, the rows added during 2026 number 75 (Xbox), 90 (PS Plus), 47 (Epic) and 55 (Humble): 267 usable rows across all four. That is the honest size of any out-of-time holdout built from this refresh, and it is smaller than the raw new-row count because the filters above remove a meaningful share.

Features

Seven columns, in a fixed order

The feature order is part of the serving contract. The backend assembles its row in exactly this sequence, so reordering the list in training silently corrupts every prediction.

metacritic_score

Critic score. Missing values fall back to the training median (or 75 if there is no median at all).

pub_te

Smoothed target encoding of the publisher — the headline feature. How long this publisher's games historically take.

pub_count

How many games this publisher has in the training fold. Tells the model how much to trust pub_te.

pub_cv

Coefficient of variation of that publisher's waits — consistent versus erratic. Missing defaults to 0.5.

rel_year

Release year, capturing drift in how these services have behaved over time.

rel_month

Release month — seasonality. Holiday releases behave differently.

rel_quarter

Release quarter, a coarser view of the same seasonal signal.

Publisher target encoding

Publisher is the strongest predictor available and also high-cardinality, with a long tail of studios holding one or two games. A raw group mean would overfit that tail badly, so it is shrunk toward the global mean:

pub_te = (sum_days + global_mean_days * K) / (count + K) K = 10.0

A publisher with 200 games keeps essentially its own average. A publisher with one game sits almost entirely on the global prior. K = 10 sets where the crossover falls.

An unseen publisher at serve time gets global_mean_days, pub_count = 0 and pub_cv = 0.5. This is deliberate: the previous generation returned confidence 0 and effectively refused to answer. Now it answers from the prior, with a wide interval that says so.

Every one of these maps is computed on the training fold only and stored inside the model bundle, so the backend reproduces the exact featurisation it was trained with. This is what keeps model and encoder from drifting apart — a desync that shipped silently once before.

The model

Quantile regression, three models per platform

Each platform trains three XGBoost regressors with objective="reg:quantileerror", at quantile_alpha 0.1, 0.5 and 0.9. Together they describe a distribution rather than a point:

P50 is the headline answer and the only one scored by MAE. P10 to P90 is an 80 percent interval: over many predictions, four in five actual arrivals should land inside it.

The interval replaced a hand-tuned confidence score that was never a real probability. The important gain is that the new one is falsifiable — you can count how often reality lands inside the band and find out directly whether the model is overconfident. A percentage that cannot be checked is decoration.

Hyperparameters

n_estimators 300 min_child_weight 3 learning_rate 0.05 subsample 0.8 max_depth 5 colsample_bytree 0.8 reg_alpha 0.1 reg_lambda 0.1 random_state 42 n_jobs -1

The backtest harness constructs its model with these same values on purpose, so the gate measures the thing that actually ships.

Bundle format

One pickle per platform, models/model_<key>.pkl, holding the three quantile models plus every featurisation map. Trained on all available data — an earlier generation shipped a model fitted on only the 80 percent training split, throwing away a fifth of the evidence for no benefit.

The serving cascade

Four tiers, first match wins

The model is the last resort, not the first. Most queries are answered by a rule, because rules are more accurate than the model where they apply.

TierTestAnswer when it fires
1Publisher is first-party for this service. Four separate branches, each with its own fixed answer — see belowA hardcoded wait, from 0 to 18 months. No model involved.
2Game is not available on the service's platform at allNot eligible. Stops nonsense predictions for hardware mismatches.
3Game has appeared on this service beforeInterval estimate from its own repeat history, using the platform's average repeat interval.
4Everything elseQuantile model: P50 plus the P10 to P90 interval.

"First-party" is not one rule and does not mean day one. It is four keyword matches on the publisher string, each returning a different fixed wait. Only core Microsoft returns zero.

Sony first-party titles are not day one on PS Plus Extra and never were — they reach the Extra catalogue a year or more after release. Only Microsoft's own studios go day one, and only on Game Pass. "No rule" means the query falls through to the historical lookup and then the model.

These fixed waits encode commercial arrangements, not stable facts

The blanket Activision-Blizzard rule has been removed. It returned a confident 3 months for every matching title, which stopped being true when Microsoft announced in April 2026 that new Call of Duty releases no longer launch into Game Pass and instead join about twelve months later. Day-one Call of Duty lasted exactly two releases, Black Ops 6 and Black Ops 7; Modern Warfare 4 (23 October 2026) is the first mainline entry to skip it.

Call of Duty is now matched on the title, because the policy covers the franchise rather than the publisher, and it is gated on release date. Only titles released on or after 2026-04-01 get the twelve-month wait. Older Call of Duty games are already on the service and already in the training data, so they fall through to the historical lookup — without that gate, a 2012 title would be predicted to arrive a year from today. Everything else Activision or Blizzard publishes now goes to the model, which reads their real and varied histories better than a fixed number did.

Note the ordering hazard behind that gate: tier 1 runs before the historical lookup, so any rule here silently overrides genuine history. Returning no answer is how a rule declines to interfere.

Still outstanding: the Bethesda branch is internally inconsistent. Its category says "Within 6 Months", its reasoning text says "Day One", and the number it returns is 3 months.

This rule encodes a commercial decision that has now changed twice in three years. It carries a review date in the source: when Modern Warfare 4 actually lands, expected late 2027, that becomes the first real evidence of the new policy and the point at which data can start replacing the rule.

This is the least trustworthy tier in the system, precisely because it hardcodes deals that change. The data now covers the whole post-acquisition period, so the model can answer these cases from evidence instead.

Tier 3 is why repeat giveaways matter so much in the data, and why silently dropping them costs more than the row count suggests.

The API returns predicted_months_low and predicted_months_high alongside the point estimate, plus projected_arrival_low and projected_arrival_high as formatted month names.

The interval is not in the interface yet

The backend returns these fields today, but no frontend surface displays them and the shared output schema is still undocumented. Until that lands, the honest-uncertainty work is invisible to users.

Measuring accuracy

Walk-forward, against baselines

Accuracy is measured by expanding-window walk-forward cross-validation: sort by arrival date, train on the past, test on the future, recompute every publisher feature on the training fold alone. Two naive baselines set the bar — global median wait, and per-publisher median falling back to global.

The rule: a model earns its keep only by beating the best naive baseline on walk-forward error. A model that loses to a median is not a model, it is overhead.

Two numbers in this codebase are not accuracy and should never be quoted as such. The in-sample MAE printed by the training stage (370 days for Xbox, 532 for PS Plus, 150 for Epic at the last recorded run) is the model scored on data it was fitted on — a sanity check that training ran, nothing more. The old random-split MAE was worse than useless: it reported 1,167 days for Xbox where honest validation says 1,796, roughly twice as optimistic, because shuffling a time-to-event target leaks the future into the past.

Known problems

Read this before trusting a refresh

These are live, reproduced, and unresolved as of this writing.

Humble text filter drops real games and admits junk

The heuristic that strips genre annotations from Humble dumps kills any two-word line where one word is a genre, and its genre vocabulary is incomplete. Measured effect on the current dump: 4 real games dropped (Settlement Survival, Nomad Survival, Hotshot Racing, Action Henk) and 23 annotation fragments admitted as fake games with names like Fps Multiplayer Action.

APPEND dedupes on name alone, discarding repeat giveaways

Epic's merge concatenates existing canonical first, then drops duplicates by normalised game name, keeping the first. A game given away twice therefore keeps only its earliest appearance. Two were lost in the August 2026 refresh: We Were Here Together (Dec 2025, again Aug 2026) and Bloons TD 6 (Aug 2023, again Jan 2026). Small in row count, but repeats are exactly what tier 3 runs on, and the loss compounds with every refresh.

Future-dated rows are announcements, not arrivals

The community spreadsheets carry "Coming Soon" entries with arrival dates in the future — 8 such rows in the August 2026 refresh. They have not happened yet. Any evaluation that treats them as observed outcomes is scoring the model against a guess.

Filtering by arrival window biases evaluation optimistic

Selecting test rows by "arrived during the window" conditions the sample on having arrived, silently excluding every slow arrival still pending. The test set fills up with fast cases and error looks better than it is. Evaluate from a frozen decision point instead: fix a date, predict the games not yet arrived, then check what happened — and treat the still-pending ones as censored rather than wrong. Survival models handle this natively; the current design does not.

Epic release dates are largely absent

The Epic source lists a giveaway date and a title, nothing else. Everything the model needs — publisher, release date, score — comes from RAWG name-matching, so an Epic prediction is only as good as that match. Epic also has the smallest trainable set of the four.

Running it

Practical notes

Open run.ipynb at the repo root and execute the stages in order. Each is an ordinary function call, so any stage can be run alone from a shell.

from pipeline import ingest, enrich, train, backtest, deploy ingest.run() # data/raw -> data/processed. No network. enrich.run() # RAWG fill -> data/canonical. Backs up first. train.run() # -> models/model_<key>.pkl backtest.run() # the quality gate. Read before deploying. deploy.run() # sync into apps/backend/

RAWG credentials are read from the environment, or from a gitignored local env file. Nothing is hardcoded and no credential belongs in a commit. Absolute machine paths do not belong in the pipeline either — everything derives from the repo root.

Before a refresh: confirm the raw dumps parse to the row counts you expect, and check that a REPLACE-mode dump carries full history rather than only the new period. A truncated REPLACE dump silently deletes years of data.

After training: read the backtest before deploying. A model that loses to its baseline should not ship.
