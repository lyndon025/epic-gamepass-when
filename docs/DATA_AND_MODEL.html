Epic Game Pass When? / Data and model reference

Arrival Model Handbook

How this system predicts when a game will show up free on Xbox Game Pass, PS Plus Extra, the Epic Games Store, or Humble Choice — what data feeds it, what it actually learns, how good it really is, and where it is still wrong.

Data as of 25 September 2026 Model quantile bundle, per platform Refresh quarterly

The question the system answers

Scope

A user types a game name and picks a service. The system answers when will this be free there — as a month, with a range around it.

That makes this a time-to-event problem, not a classification one. The quantity being predicted is the number of days between a game's release and the day it lands on the service. Framing matters more than it looks: because the thing being predicted is a duration measured forward from the past, any validation that shuffles rows at random lets the model see the future. That mistake was in this codebase for most of its life, and correcting it changed the reported error by roughly a factor of two.

Four services, four separate models. Nothing is shared between platforms except the code — each has its own dataset, its own target distribution, and its own trained bundle.

The four datasets

Canonical schema

Whatever the source looks like, ingest flattens it to eight columns. Every downstream stage reads only these.

game_name title as scraped; the join key everywhere release_date MM/DD/YYYY, RAWG-filled where the source lacks it Added to Service MM/DD/YYYY, the event date and the target's endpoint Removed from Service MM/DD/YYYY or blank; drives catalogue status at serve time metacritic_score numeric, sparse publisher RAWG-filled; comma-separated, first value wins developer RAWG-filled; carried, not modelled System platform string from the source

The catalogue sheets are read by column position

Ingest reads the two sheets by position rather than header name, so fetch checks the header row against the expected positions and refuses to continue if the layout has shifted. The xlsx export is used rather than CSV because it carries the underlying day-precision dates instead of the displayed month-precision text; dates are written out explicitly as MM/DD/YYYY.

Popularity

pipeline/popularity.py records each catalogue game's RAWG follower count (added) in data/canonical/rawg_popularity.csv. Titles are cleaned first (edition suffixes, platform tags, numerals), the top five search results are compared on name and release year, and every row carries a confidence grade; only high and medium matches are used, sequels never match their predecessor, and in-game item giveaways are skipped. About 92% of games carry a usable count. Raw counts mostly encode release year, so any use ranks a game within its release year.

The count is not used by the forecast. Tested as a feature under the walk-forward gate it moved error by a few percent in both directions across services, and because it is measured today, after most games have already arrived, part of any relationship would be the arrival raising the count rather than the reverse.

How data moves

Seven stages

The pipeline is an importable Python package; run.ipynb at the repo root runs each stage in order.

Google Sheets fetch data/raw/ ingest data/processed/ enrich data/canonical/ --------> xlsx + csv --------> *_Processed.csv --------> Epic/Xbox/PS/HB.csv | train + backtest v apps/backend/ deploy models/model_<key>.pkl + arrival_hazard.json + data_status.json serving copy <-------- (also to frontend/public)
  • fetch downloads the Game Pass and PS Plus catalogue sheets, validates their layout, and records the collection date. Epic and Humble listings are added to data/raw/ by hand.
  • ingest parses each raw source into the eight-column schema. Edition names are normalised at lookup time, not here.
  • enrich fills publisher, developer, release_date and metacritic_score from the RAWG API, then merges into canonical. Its lookup cache is built from the existing canonical files, so only new titles cost a request.
  • train fits and calibrates one bundle per platform, on all available data.
  • backtest scores the model against naive baselines on time-ordered folds. It is the release gate.
  • deploy copies canonical data and bundles into apps/backend/, and regenerates two derived tables from the same data: arrival odds by game age, and the data-status file the site displays.
  • preflight exercises the deployed backend in-process across every serving path. It must pass before a push.

data/processed/ is gitignored and regenerable. Canonical CSVs, bundles and both derived tables are tracked, because they are what the backend serves.

The target

What the model is fitted on

The label is days_to_service, the gap between release and arrival:

days_to_service = (Added to Service) - (release_date) in days rows are dropped unless: days_to_service is not null days_to_service >= 1 day-one arrivals and bad dates are excluded days_to_service > 60 launch-window deals are answered from the catalogue primary_publisher not in ("Unknown", "") primary_publisher = publisher.split(",")[0].strip()

Models are fitted on log(days) and exponentiated back at prediction time. That choice matters when reading errors: the model is being optimised for proportional accuracy, so being six months off on a three-year wait counts as a smaller mistake than being six months off on a two-month wait. Any error analysis should be done in log space and only then reported in days.

The 60-day rule defines the question the forecast answers: how long a game waits without a launch deal. Launch deals are agreed before release and appear in the catalogue as dated upcoming arrivals, which the site reports as fact; they make up a large share of recent Game Pass arrivals, and left in they would teach the model that any recent release arrives within weeks. The same rule applies to training, to the walk-forward gate and to the scorecard, so every number on this page measures the question actually asked.

After these filters the trainable set is 1,821 rows for Xbox, 2,486 for PS Plus, 1,080 for Humble and 590 for Epic. Median wait varies widely by service — 18 months on Humble against 43 on Epic — which is why the four models share no parameters.

Features

Seven columns, in a fixed order

The feature order is part of the serving contract. The backend assembles its row in exactly this sequence, so reordering the list in training silently corrupts every prediction.

metacritic_score

Critic score. Missing values fall back to the training median (or 75 if there is no median at all).

pub_te

Smoothed target encoding of the publisher — the headline feature. How long this publisher's games historically take.

pub_count

How many games this publisher has in the training fold. Tells the model how much to trust pub_te.

pub_cv

Coefficient of variation of that publisher's waits — consistent versus erratic. Missing defaults to 0.5.

rel_year

Release year, capturing drift in how these services have behaved over time. Clamped to four years before the newest arrival in the data: a game released last year is only in the data if it has already arrived, so recent years show only short waits, and the clamp keeps that edge from being read as a trend.

rel_month

Release month — seasonality. Holiday releases behave differently.

rel_quarter

Release quarter, a coarser view of the same seasonal signal.

Publisher target encoding

Publisher is the strongest predictor available and also high-cardinality, with a long tail of studios holding one or two games. A raw group mean would overfit that tail badly, so it is shrunk toward the global mean:

pub_te = (sum_days + global_mean_days * K) / (count + K) K = 10.0

A publisher with 200 games keeps essentially its own average. A publisher with one game sits almost entirely on the global prior. K = 10 sets where the crossover falls.

An unseen publisher at serve time gets global_mean_days, pub_count = 0 and pub_cv = 0.5. It answers from the prior, with a wide interval reflecting how little is known, rather than declining to answer.

Every one of these maps is computed on the training fold only and stored inside the model bundle, so the backend reproduces the exact featurisation it was trained with. This is what keeps the model and its featurisation from drifting apart, which is the failure mode that makes a retrained model quietly wrong.

The model

Quantile regression, three models per platform

Each platform trains three XGBoost regressors with objective="reg:quantileerror", at quantile_alpha 0.1, 0.5 and 0.9. Together they describe a distribution rather than a point:

P50 is the headline answer and the only one scored by MAE. P10 to P90 is an 80 percent interval: over many predictions, four in five actual arrivals should land inside it.

The interval is falsifiable, which is the point of it: you can count how often reality lands inside the band and find out directly whether the model is overconfident. A confidence figure that cannot be checked is decoration.

Hyperparameters

n_estimators 300 min_child_weight 3 learning_rate 0.05 subsample 0.8 max_depth 5 colsample_bytree 0.8 reg_alpha 0.1 reg_lambda 0.1 random_state 42 n_jobs -1

The backtest harness constructs its model with these same values on purpose, so the gate measures the thing that actually ships.

Bundle format

One pickle per platform, models/model_<key>.pkl, holding the three quantile models plus every featurisation map. Trained on all available data: withholding a slice would deny the shipped model evidence it should have, and honest accuracy is measured by walk-forward and out-of-time holdout instead.

The serving cascade

First match wins

The model is the last resort, not the first. Where a published fact or a rule settles the question, it answers before any forecast is made.

TierTestAnswer when it fires
1Publisher is first-party for this service, or the title is a post-policy Call of Duty releaseA fixed, published outcome. No range.
2Game is not available on the service's platformNot eligible.
3Game appears in this service's history (edition suffixes normalised)Catalogue status, an announced date, or the service's measured return rate
4Everything elseCalibrated forecast: P50 plus the 80% band, or arrival odds once the estimate has passed

Titles released before a policy's start date are not claimed by it; they fall through so their real history answers. Tier 1 runs before the history lookup, so an ungated rule would override genuine arrival records.

Tier 3: history

For Game Pass and PS Plus, membership is stated only as far as the data proves it. A stint with no removal date means the game was in the catalogue on the collection date, and the answer is qualified that way. An announced removal date is reported as a departure date; an arrival dated after the collection date is reported as announced. Epic and Humble are one-off events, so a blank removal date carries no meaning there.

A past appearance otherwise answers from the service's measured return rate, computed from the data at startup: 7 of 621 Epic giveaways (1%), 158 of 2,115 Game Pass titles (7%) and 312 of 2,397 PS Plus titles (13%) have ever reappeared. Only a game that has returned before and is still within its own rhythm gets an interval-based forecast.

Tier 4: forecast and arrival odds

While the estimate is in the future, the answer is the P50 month with its band, and the headline wording follows the band width. Once the estimate has passed, the answer is chosen from arrival_hazard.json: for games of that age not yet on that service, the share that arrived within the following year.

AnswerCondition
month / year / floor / suppressedEstimate ahead; band under 24, 24–48, 48–96, over 96 months
windowEstimate passed, yearly arrival chance 8% or more; or due within ~6 weeks with the window open
fadingEstimate passed, yearly chance 3–8%
unlikely-soonEstimate passed, yearly chance under 3%

The odds table is recomputed by deploy from the same data the backend serves. Field-level detail is in docs/CONTRACT.md.

Measuring accuracy

Walk-forward, against baselines

Accuracy is measured by expanding-window walk-forward cross-validation: sort by arrival date, train on the past, test on the future, recompute every publisher feature on the training fold alone. Two naive baselines set the bar — global median wait, and per-publisher median falling back to global.

The rule: a model earns its keep only by beating the best naive baseline on walk-forward error. A model that loses to a median is not a model, it is overhead.

Walk-forward MAE in days, model against the stronger of the two naive baselines. The bar for shipping is beating it.

One number in this codebase is not accuracy and should never be quoted as such: the in-sample MAE printed by the training stage is the model scored on data it was fitted on — a sanity check that training ran, nothing more. A random-split MAE is worse than useless on this target, running roughly twice as optimistic as honest validation, because shuffling a time-to-event target leaks the future into the past.

Skill is 1 − MAEmodel / MAEpublisher baseline. The ≤N columns are the share of P50 estimates within N years of the true arrival. Coverage is the share of arrivals inside the calibrated P10–P90 band, against a nominal 80%.

Coverage and band width are read together. Any coverage target is reachable by widening the band, so coverage alone cannot distinguish a calibrated model from a vague one — which is why the serving layer softens its wording as the band widens rather than presenting every band as equally precise.

Humble's lower skill reflects a strong baseline rather than a weak model: its waits are short and tightly clustered, so the publisher mean is already a good guess and the headroom is small.

Arrival estimates are conditioned on arrival, since every training row is a game that did arrive. For titles well past their estimate, the serving layer therefore defers to the measured arrival odds by age rather than to the point estimate.

Limitations

What the current design does not capture

Platform availability is not in the data

The canonical datasets carry no field for which platforms a game shipped on. The serving layer receives that from RAWG at request time, but the training data and the arrival-odds table cannot filter on it, so their candidate pools include some games that could never have arrived on a given service. The effect is to pull measured odds slightly low.

Arrival odds are service-wide, not game-specific

The yearly arrival chance used once an estimate has passed is a base rate by game age for the whole service. It does not account for publisher or genre. It answers "games of this age, on this service" rather than "this game".

Evaluation uses arrived games only

A holdout can only contain games that did arrive, so accuracy is measured on the arrival-conditioned distribution. Ranking-based measures such as concordance, and median rather than mean error, are the more robust readings for that reason.

Epic and Humble metadata depend on name matching

Both sources list only a date and a title. Publisher, release date and score come from RAWG name matching, so their quality follows the match. Both also have the smallest trainable sets of the four.

Membership is current only to the collection date

Catalogue status is true as of the last fetch. The site states it that way, and a quarterly refresh bounds how stale it can be.

Running it

Quarterly refresh

Before running, add the new Epic weeks and Humble months to their files in data/raw/ (the notebook's first cell describes the layout). Then run run.ipynb top to bottom, or the stages directly:

from pipeline import fetch, ingest, enrich, train, backtest, deploy, preflight fetch.run() # Game Pass + PS Plus sheets -> data/raw. Stops if the layout changed. ingest.run() # data/raw -> data/processed. No network. enrich.run() # RAWG fill -> data/canonical. Backs up first. train.run() # -> models/model_<key>.pkl, calibrated backtest.run() # the release gate. Every platform must beat its baseline. deploy.run() # sync into apps/backend/, regenerate odds + data status preflight.run() # must return 0 before pushing

RAWG credentials are read from the environment, or from a gitignored local env file. Nothing is hardcoded and no credential belongs in a commit. Paths derive from the repo root.

Pushing to dev redeploys the dev environment. Production is a separate, manual promotion.
